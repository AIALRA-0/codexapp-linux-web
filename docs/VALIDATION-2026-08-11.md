## 大任务白屏是怎么修的

### 发现的问题

Trillium Note 原始任务文件约 613 MB（约 585 MiB）。官方引擎可以解析它，但返回页面的数据约 168 MB

旧宿主把这 168 MB 当成一条 WebSocket 消息发送。消息超过客户端默认上限后，连接会以“消息过大”关闭。用户看到的表现就是一直加载、突然白屏或任务打不开

### 采用的修复

最新版官方界面本身已经支持 `codex-host-chunked-message-v1` 分块协议

宿主现在：

1. 小消息保持原样发送
2. 大消息转换成官方支持的结构化分块
3. 每收到浏览器确认后再发送下一块
4. 浏览器按官方协议还原为原始结果，再交给未经修改的官方界面

这不是另一套历史数据库，也没有修改官方页面组件。对话的唯一事实来源仍然是官方 Codex 任务文件

## 真实测试结果

测试对象不是人工生成的小样本，而是迁移后的完整 Trillium Note 任务

| 指标               |              结果 |
| ------------------ | ----------------: |
| 原始任务文件       |         约 613 MB |
| 返回轮数           |            131 轮 |
| 页面结果大小       | 168,468,457 bytes |
| 连接建立           |             7.8 s |
| 官方引擎读取       |            74.9 s |
| 宿主传输与组装     |         约 38.2 s |
| 完整任务读取       |           113.1 s |
| WebSocket 异常关闭 |              0 次 |
| 服务重启           |              0 次 |
| 测试后服务状态     |              正常 |

把分块从 256 KiB 调整为 1 MiB 后，宿主额外时间从约 52 秒降到约 38 秒。官方引擎读取时间本身会随冷启动和服务器负载波动

## 为什么没有直接做缓存

把 168 MB 结果缓存下来确实可能让第二次打开更快，但任何失效规则遗漏都会重新制造“任务只显示旧内容”的问题

本轮优先修复完整性和稳定性：每次仍读取官方原始任务，只优化传输方式。后续若做缓存，必须同时证明新增消息、分支、压缩、归档、恢复和服务重启都不会读取旧结果，否则不进入生产

## 还不能承诺什么

当前可以承诺“大任务不会因为单条消息过大而白屏”，不能承诺“约 613 MB 任务快速打开”

后续性能验收必须分别记录：

1. 官方引擎读取时间
2. 服务器宿主处理时间
3. 服务器到用户浏览器的公网时间
4. 浏览器组装和渲染时间

只有宿主处理时间接近可忽略，剩余等待主要来自官方引擎和真实网络时，才能认为架构延迟已经压到合理范围
